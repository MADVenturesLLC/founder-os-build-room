Part B: The changes
B1. Requests. Every request the driver makes ends within 30 seconds or fails. A read (GET) that fails without an HTTP answer, by a network error or that timeout, or that is answered 502 or 504, is tried again after 5, 10, 20, 40 and then every 60 seconds, for at most 10 minutes from its first failure; each retry prints one line with the time, the route and the reason, and never a token or a body. After 10 minutes the read fails as now and the run is judged as now. A write (POST) is never tried again: a write whose answer was lost may have taken effect, so it fails as now. No other answer is retried, 503 included, because the control plane answers 503 for states that are not transient. The round's own timeout, my decision time of 4 hours and the deployment check are unchanged: a change of deployment still interrupts the run.
B2. Reading the plan. A new route, GET /control-plane/rooms/:roomId/plan, guarded by the control plane's API token, answers the plan the room's latest T3 submitted, as the plan store returns it and judges it again: { roomId, commandId, planHash, document }. A room with no T3 answers 404, and the route writes nothing. When a round reaches plan_review, the runner reads that route, checks that its planHash is the round's, writes the document to its evidence directory as plan-<planHash>.json, never overwriting a file, and prints the file's path and the plan's hash. If the read or the check fails, the runner prints so and waits for my decision as now; it never decides.
