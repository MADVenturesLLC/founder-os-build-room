connection string:
  1. One function decides the connection settings for a URL. TLS is

     other URL parameter, including sslmode=no-verify, sslmode=require
     with uselibpqcompat=true, ssl=0 or ssl=false, can turn TLS off or
     turn verification off. The connection string reaches
     node-postgres in a form in which it cannot override that
     decision.
  2. The control plane's pool (packages/control-plane/src/db.ts) and
     the administrative runner's two connections
     (packages/control-plane/src/migrate-cli.ts) use that function.
  3. The comments in db.ts that say an explicit ssl option overrides
     the connection string are corrected: node-postgres applies the
     parsed connection string over the explicit option.
  4. The tests prove the rule by reading the settings node-postgres
     actually connects with, not the pool's options object: hosted
     URLs with sslmode=require, prefer, verify-full, no-verify,
     require with uselibpqcompat=true, ssl=0 and no sslmode all
     verify; sslmode=disable and loopback hosts do not use TLS; a
     password that merely contains "localhost" still verifies. The
     same cases hold for migrate-cli's connections. At least the
     no-verify and ssl=0 cases fail against main at 06c608e and pass
     with the change. The existing TLS-defaults test, which reads the
     pool's options object, is rewritten to read the effective

WHY
db.ts sets ssl = { rejectUnauthorized: true } so that a pasted
connection string cannot silently weaken certificate checking. It
does not do that. node-postgres lets the parsed connection string
override an explicit ssl option, and db.ts only refuses to set TLS
when the URL says sslmode=disable. With pg 8.13.1 and
pg-connection-string 2.14.0, as on main today (builder probe,
2026-10-10):
  - sslmode=no-verify gives rejectUnauthorized false: encrypted, not
    verified;
  - ssl=0 gives ssl false: no TLS at all;
  - sslmode=require with uselibpqcompat=true gives rejectUnauthorized
    false, and from pg 9 sslmode=require alone will too.
Production's DATABASE_URL holds prefer, require or verify-ca (the boot
log prints a warning only for those), all verified today, so
production is not exposed now. The control is the problem: one edited
or pasted URL would turn verification off with no error and no log
line. The existing test did not catch it because it reads the pool's
options object, which is not what node-postgres connects with.
