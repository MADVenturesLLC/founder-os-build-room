B2. My rulings on section 8 of the note.
  R1. Phase 3's counted-run harness stays macOS-only. Lifting it is a change to the counted-run gate and needs its own act.
  R2. On Linux the Gateway keeps the macOS-style directory, ~/Library/Application Support/founder-os/gateway, with no operating-system branch.
  R3. For the Linux custody backend (P1) and the Linux redaction key source (P3), CI exercises the branch against a fake systemd-creds runner, and the real backend is exercised by the real Linux custody suite at certification on the PC. I accept that as meeting B2's requirement for those two branches. A macOS CI job, and its cost, is decided in the implementation act.
  R4. Not decided by this act. Whether the PC's redaction HMAC key is a new value or the Mac's is decided by my act that mints it, which comes after the builder reports whether redaction tokens are compared across hosts.
  S1. An egress allowlist enforced by a proxy outside the sandbox, behind a network namespace with no other route out, meets clause 2's egress allowlist.
  S2. A private tmpfs for each task, discarded when the task ends, is inside clause 2's write allowlist.
  S3. No shell, hooks disabled and the submodule allowlist are accepted as enforced by the Gateway's spawner and git configuration, on both operating systems.
  S4. The native code for Landlock and seccomp is built in the repository, kept small, and reviewed with the sandbox.
  S5. Loading the AppArmor profile on the PC is its own act of mine, which I run.
  S6. The sandbox is built with the first Gateway path that runs a task, on macOS and Linux together, not in the implementation of B7.
  S7. B4's "and nothing else" means reading (a): a confining launcher profile that lists only what bubblewrap uses, with a child profile, reached by an exec transition, that allows no user namespaces, capabilities or mounts.

B3. Versions. Under my act's B9, the Gateway runs on Node v22.23.2 and Bun 1.4.2 on the PC and on every Mac, as section 7 of the note fixes.
