Part B: The change
B1. What is re-asked. A round re-asks once when its attempt fails as one of these, and only these:
  (a) plan_invalid, where the refusal reason judgeRoundPlan gave is of kind schema, scope_path or encoding (not not_ready);
  (b) planner_reported_failure, where the Gateway's report names one of unparseable_plan, malformed_output, no_result, agy_error or oversize (B2).
If the re-ask's attempt fails, for any reason, the round fails as it does today. A round holds at most one re-ask, and its attempts stay within MAX_ROUND_ATTEMPTS. The re-ask is not a transport retry: retryBudgetTransition is not consulted for it, and the not_sent rule of Q8 is unchanged.
B2. The Gateway's report. In packages/gateway-protocol/src/planner.ts, the failed member of PlannerResultWire gains an optional member reason, one of: agy_error, no_result, unparseable_plan, model_switched, malformed_output, timed_out (the executor's run outcomes other than a plan), and oversize (a finished result too large for its report, boundedResult in planner-worker.ts). Any other value or member is refused, and a failed report without reason stays valid. The Gateway sends reason when the run ended in one of those outcomes, and none when it failed in any other way. The control plane journals it on the attempt's failed row as the evidence reference planner-failure/<reason>.
B3. The re-ask's work. PlannerWorkWire gains an optional member reask, which is exactly one of:
  (a) { refused: "plan_invalid", reason, refusedPlan }: reason is the refusal reason of B1(a) in the shape PlanRefusalReason has at 8a62e2c, with each violation's code among ViolationCode, at most PLAN_REFUSAL_VIOLATIONS_KEPT violations, and each path a string of at most 1,024 characters; refusedPlan is the document the control plane refused, a plain JSON object whose JSON text fits MAX_PLANNER_PAYLOAD_BYTES in UTF-8;
  (b) { refused: "planner_reported_failure", reason }: reason one of the five of B1(b).
Any other shape is refused. Both sides validate with this one implementation, as now. A work without reask is unchanged.
B4. The control plane. In runRound, when the attempt it has just run fails as B1 names and the round has made no re-ask, the control plane opens the round's next attempt in the same call, under the room lock, as openNextAttempt opens any attempt: a new command id from plannerCommandIdFor with the next attempt number, journaled before any contact. Its evidence references add retry-of/<the failed command id> and retry-reason/<plan_invalid or planner_reported_failure> (item 5: each retry is logged with its reason). A revision round reads its earlierPlan again, under B2 of FOUNDER-ACT-20261109-BR-PLANNER-REVISION-CONTEXT. The work carries B3's reask. The attempt then runs as any other, and runRound returns its outcome. On a plan_invalid failure the control plane also journals, on the failed row, refused-plan/<the document's planHash>, when planHash can compute one. A re-ask opens only in the call whose attempt failed: no later call, recovery or restarted control plane opens one, and a round whose re-ask could not open is failed as today.
B5. The prompt. In plannerPrompt in packages/gateway-daemon/src/agy-planner-executor.ts, when the work carries reask, these lines are added, each a line of its own, after the revision lines when there are any and otherwise after the scope paths, and before the blank line that opens HOW TO WRITE THE PLAN:
  (blank line)
  YOUR EARLIER ANSWER TO THIS REQUEST WAS REFUSED
  You have answered this request once already. The control plane refused that answer, for this reason:
  the reason lines of B6
Then, for a plan_invalid re-ask:
  Your refused answer follows, exactly as the control plane received it. Correct what the reason names, change nothing else, and give the whole corrected plan as your answer. Rules 1, 2 and 5 below apply to what you change.
  (blank line)
  REFUSED ANSWER
  the refused answer as one line of JSON (JSON.stringify of refusedPlan)
and for a planner_reported_failure re-ask:
  Answer the request again, in full, following every rule below.
B6. The reason lines.
  schema: "It does not satisfy the schema in the ANSWER section. Each line below names a place in that answer, as a JSON pointer, and what is wrong there:", then one line "- <path>: <code>" per violation kept, ending " (found <found>, limit <bound>)" for a length violation that carries both; then, when the refusal counted more violations than it kept, "- and <n> more".
  scope_path: "Its scope_paths entry at index <index> is not a valid repository path." With no index: "Its scope_paths are not valid repository paths."
  encoding: "It holds a number that is not a whole number, or a negative zero, which a plan cannot carry."
  unparseable_plan: "It was not one JSON object."
  oversize: "It was too large to send. Keep within rule 6 below."
  malformed_output, no_result and agy_error: "No answer reached the control plane."
B7. Every other line of the prompt stays word for word and in its order. A prompt for work without reask is unchanged, byte for byte, from 8a62e2c.
