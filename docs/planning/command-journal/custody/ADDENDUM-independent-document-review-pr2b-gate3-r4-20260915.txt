CORRECTION 1 (HISTORICAL — NEVER DISPATCHED) — the R3-to-R4 delta was stated in an ambiguous unit

The brief says: "R4 amends R3 by pure insertion: 18 hunks, 17 insertions
and one replaced line (the title designator)."

"17 insertions" is a hunk count. Read as a line count, which the
sentence invites, it cannot be reconciled with the sizes the brief
itself gives.

Line counts, from `git diff --numstat` between the two blobs on main.
These do not depend on how the diff is rendered:

  lines added      335
  lines removed    1      (the title designator, R3 -> R4)
  net              +334
  R3               2285 lines
  R4               2619 lines   (2285 + 335 - 1)

Hunk counts do depend on rendering, and the brief gave one as though it
were fixed. `--numstat` reports no hunks at all. Counting `@@` markers:

  18 hunks at --unified=0    (17 insertion + 1 replacement)
  14 hunks at the default -U3

Cite the line counts. Treat any hunk count as a description of one
rendering, not a property of the change.

"Pure insertion" is also loose: one hunk replaces a single line. The
claim to verify is that no R3 line other than the title designator was
changed or removed, and that R3's rows are retained rather than
replaced.

CORRECTION 5 (HISTORICAL — NEVER DISPATCHED) — the verdict vocabulary had no way to report a brief defect

The brief fixes the first output line to PASS or REQUEST CHANGES /
DOCUMENT REVIEW FAILED. Both are verdicts on the act. A reviewer blocked
by a defect in the brief itself — for instance unable to locate the
implementation plan Q6 needs, which is exactly what correction 2
repairs — had no vocabulary for that, and would have had to return
REQUEST CHANGES against the act for a fault in the brief. That would
corrupt the record this review feeds.

A third first-line verdict is therefore available:

  CANNOT COMPLETE — BRIEF DEFECT

Use it when the brief or this addendum, not the act, prevents answering.
Name the question, name what is missing, and answer whatever other
questions you can. It is not a verdict on the act and does not count as
a failed document review.

CORRECTION 6 (HISTORICAL — NEVER DISPATCHED) — a command in the
dispatched text does not run as written

The brief's "Read it from committed truth, not a working tree" block
gives, at line 66 of the brief as landed — line 24 of the dispatched
text, the frame this addendum otherwise uses:

  git show origin/main:<path above> > /tmp/r4.md

`<path above>` is not a placeholder the shell ignores. `<` and `>` are
redirection operators, so bash parses `<path` as input redirection and
the line dies with `syntax error near unexpected token '>'` before
git runs. Verified with `bash -n`.

The placeholder has a second defect the shell never reaches: the path
it points at is itself wrapped, across dispatched-text lines 15 and 16
(landed 57 and 58), with continuation indentation, so a
reader substituting by hand must rejoin two lines and strip leading
whitespace, with no hash on the rejoined result to catch an error. The
single-line `P=` form below fixes both.

This is the same defect class the banner warns about and the receipt
records fixing in its own recipe. It was missed in the dispatched text
because the earlier rounds only inspected the banner and the receipt.
It is corrected here rather than in the brief, because the dispatched
bytes are pinned at 3aac089e and must not change.

The command should read:

  git fetch origin main
  P=docs/planning/command-journal/custody/DRAFT-founder-authorization-pr2b-gate3-trancheB-journal-authority-r4-20260914.md
  git show "origin/main:$P" > /tmp/r4.md
  sha256sum /tmp/r4.md      # must equal 466469cc...13dae

An earlier revision of this correction dropped the `git fetch origin
main` the original block carries at dispatched-text line 23 (landed
65). Without it
origin/main may be stale and the check can pass or fail against the
wrong bytes. It is restored above.

Whether the reviewer hit this is not known from here. The review
completed, so the act's bytes were obtained by some route; which route
is not recorded.
