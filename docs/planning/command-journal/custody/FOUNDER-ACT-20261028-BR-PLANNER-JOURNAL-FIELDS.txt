Part A: What this act is for
A1. Amendment 5 B2 says the change B1 needs is made in a Build Room pull request that a later act of mine directs. This is that act. It directs the work in two pull requests, in the order Part D sets.
A2. Contract §6.2 (docs/command-journal-contract.md, v0.17) requires each hashed serialization to be specified, versioned with golden vectors, and ratified before the hashing code that implements it. Adding fields to the command row changes the byte grammar of BRJ:c:1, and that spec says such a change takes a new spec version with a new identifier. So the spec is written and ratified first, and the code follows.

Part B: Rulings on reading Amendment 5 B1
B1. Which event carries the fields. Both fields are carried on the command's `dispatched` event, the event the control plane journals when the Gateway answers that the work was accepted. They are not carried on the outcome event (`completed`, `failed` or `resolved`).
    Reason: B1 covers "every command whose work the executor sent". A command that was sent and whose daemon then stopped mid-run is answered as lost, and no outcome event carrying the Gateway's report is ever journaled for it. Carrying the fields only "with the command's outcome", read literally, would leave exactly those commands without them. The executor has read the init event before it answers accepted, so both fields are known when `dispatched` is journaled. This act reads "with the command's outcome" in B1 as "with the command's journaled events" to that end. Amendment 5 is not otherwise changed.
B2. Field names and presence. The two journal fields are `init_model` and `provider_conversation_id`. On the wire, the Gateway's accepted answer carries `initModel` and `conversationId`. On `dispatched` they are present exactly when the accepted answer carries them. For the agy lane (`antigravity:google`, Gateway 1880c12d), the control plane rejects an accepted answer that lacks either field, or carries an empty or overlong one, and journals the command `unresolved`: the work may have been sent, and the record of what served it is missing. They are absent from every other event type.
B3. Classification. The conversation id is an opaque provider identifier, not credential material, under contract §6.1, and is journaled as read.

Part C: Scope
C1. Paths the two pull requests may change:
    - packages/journal/ (the row type, the validator, the BRJ:c:2 spec and its golden vectors, and chain verification across the cutover)
    - docs/command-journal-contract.md (v0.18: §2 gains the two fields; §6.2 names BRJ:c:2)
    - packages/control-plane/src/planner-loop.ts, journal-store.ts, migrations.ts (a new migration adding two nullable columns)
    - packages/gateway-protocol/src/planner.ts (the accepted answer gains the two fields)
    - packages/gateway-daemon/src/planner-worker.ts and agy-planner-executor.ts (carrying the fields from the executor's start to the accepted answer)
    - the tests for each
C2. Mixed chain. Rows journaled before the cutover stay BRJ:c:1 and verify under BRJ:c:1. Rows from the cutover are BRJ:c:2. The verifier selects the spec for each row by a marker recorded with the row, never by guessing; rows carry no such marker today (one spec id, BRJ:c:1, is a constant), so pull request 1 defines it, and a chain that switches back from BRJ:c:2 to BRJ:c:1 fails verification. Existing rows are never rewritten.
C3. Not in scope: any other journal field, any other event type, any other lane, provider or Gateway, and anything Amendment 5 Part C excludes.
