# Serialization contract (a) — normalized command envelope, version 1

Status: implementation serialization specification under
`docs/command-journal-contract.md` v0.17 §6.2, ratified through the pull
request that carries it. Spec identifier, fixed inside the canonical
bytes: `BRJ:a:1`. This document creates no governance authority; on any
conflict the command-journal contract governs.

Implementation: `packages/journal/src/envelope.ts`. Golden vectors:
`packages/journal/vectors/envelope.json`, generated by the
implementation, never hand-authored.

## Purpose

Defines the canonical byte sequence of the normalized command envelope
(contract §2 element 6) and therefore `envelope_digest` = SHA-256 over
these bytes, rendered as 64-character lowercase hexadecimal with no
prefix and no separators (contract §6.2).

The envelope is the post-redaction safe representation of a governed
command (contract §6.1). Credential material, tokens, secret environment
values, and private keys must never appear in any field. Redaction runs
before the journal write; enforcement of that rule belongs to the write
path (step 2b and later), not to this byte specification.

## Non-retroactivity (ruled 2026-09-01)

Later schema ratifications constrain which envelopes are valid; they
never alter this encoding. Any change to the byte grammar below requires
a new spec version with a new spec identifier, and golden vectors bind
to the version that generated them.

## Byte primitives

- `u32be(n)`: 4-byte big-endian unsigned integer; `n` in `[0, 2^32 - 1]`.
- `utf8(s)`: the UTF-8 encoding of string `s`, which must be well-formed
  Unicode: a string containing a lone UTF-16 surrogate has no canonical
  form and is rejected before encoding (an unpaired surrogate would
  otherwise be replaced by U+FFFD, letting two distinct inputs collapse
  to one byte sequence and share a digest). Rejected inputs produce no
  golden vector.
- `lp(s)` (length-prefixed string): `u32be(byte length of utf8(s))`
  followed by `utf8(s)`.
- String field: `[tag byte]` `[presence byte]` where presence is `0x00`
  (absent, no further bytes) or `0x01` followed by `lp(value)`.
- Array field: `[tag byte]` `[0x01]` `u32be(count)` then `lp(item)` for
  each item in recorded order. An empty array is present with count 0 —
  structurally distinct from absent. Order is never re-sorted.

Field presence is structural: absence is the dedicated `0x00` presence
byte, never a sentinel value (contract §6.2).

## Canonical byte sequence

`lp("BRJ:a:1")` followed by the fields below, in exactly this order:

| Tag | Field | Kind | Presence |
| --- | --- | --- | --- |
| `0x01` | `envelope_version` | string | required; must be `1` under this spec version |
| `0x02` | `command_kind` | string | required, non-empty |
| `0x03` | `argv` | array of strings | required; may be empty; recorded order |
| `0x04` | `target_repository` | string | optional; non-empty when present |
| `0x05` | `scope_ref` | string | optional; non-empty when present |

Required fields always carry presence byte `0x01`. Every field above
appears in every canonical form, present or absent — the grammar is
positional and total, so two envelopes differing in any field, in any
argv ordering, or in presence versus absence produce distinct bytes.

## Digest

`envelope_digest` = SHA-256 over the canonical byte sequence, as
64-character lowercase hexadecimal.

## Field-set rationale

The envelope field set is journal-owned spec substance under §6.2's
delegation (ruled 2026-09-01, escalation 2 on the PR 2a derivation
plan): minimal and versioned. The intended and observed routing
identities are not envelope fields; they are row fields of the
command-class event row per contract §2 element 4.
