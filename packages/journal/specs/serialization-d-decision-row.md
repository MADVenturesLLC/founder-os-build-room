# Serialization contract (d) — decision-class record row, version 1

Status: implementation serialization specification under
`docs/command-journal-contract.md` v0.17 §6.2, ratified through the pull
request that carries it. Spec identifier, fixed inside the canonical
bytes: `BRJ:d:1`. This document creates no governance authority; on any
conflict the command-journal contract governs.

Implementation: `packages/journal/src/decision-row.ts` with chain
framing in `packages/journal/src/chain.ts`. Golden vectors:
`packages/journal/vectors/decision-row.json` and the mixed chain in
`packages/journal/vectors/chain.json`, generated by the implementation,
never hand-authored, covering both `plan_hash` presence shapes
(contract §6.2).

## Purpose

Defines the canonical byte sequence of the complete decision-class
record row (contract §2; Founder ruling 2026-09-01, §12 option (b)). A
decision record is a single event, terminal by construction, with no
state machine, chained over the one `seq` space by the same framing as
command rows. Contract §2 elements 1, 4, 8, and 9 are not applicable to
the class: the row shape has no such fields, so no encoder can emit
them.

## Chain framing and why it rides in 2a

`chain_hash` = SHA-256 over the prior row's chain hash rendered as its
64 lowercase-hex ASCII bytes (the 64-ASCII-zero genesis constant for
the first row) followed by the row's canonical byte sequence per this
specification or the (c) specification, as the row's record class
determines (contract §6.2). The pure framing function rides in step 2a
because the §6.2 chain vectors cannot be generated without it; the
production hashing path — append protocol, chain head, store — is step
2b (ruled 2026-09-01, condition 2 on the PR 2a derivation plan).

## Byte primitives

Identical to spec (c): `u32be`, `utf8`, `lp`, string fields with
structural presence bytes (`0x00` absent, `0x01` present), and pair
fields (`[tag]` `[0x01]` `lp(first)` `lp(second)`). Absence is never a
sentinel value.

## Canonical byte sequence

`lp("BRJ:d:1")` followed by the fields below, in exactly this order:

| Tag | Field | Kind | Presence |
| --- | --- | --- | --- |
| `0x01` | `record_class` | string | required; always `decision`; the explicit class discriminator inside the canonical byte input (contract §2, §6.2) |
| `0x02` | `seq` | string | required; canonical ASCII decimal, no leading zeros, at least 1 — the one shared `seq` space |
| `0x03` | `decision` | string | required; `plan.revision_requested` (T4), `plan.approved` (T5), or `founder.cancel` (T22) |
| `0x04` | `actor_id` | string | required; always `founder` |
| `0x05` | `recorded_state` | string | required; a ratified `DEC-20260815-11` state name; never terminal; `PLAN_REVIEW` for T4/T5 |
| `0x06` | `prior_state` | string | present exactly when `recorded_state` is `RECONCILING`; never `RECONCILING`, never terminal |
| `0x07` | `plan_hash` | string | presence derived below; 64 lowercase hex when present |
| `0x08` | `authorization_ref` | string | required, non-empty |
| `0x09` | `lifecycle_event_ref` | pair | required; (`room_id`, `event_id`), contract §1.4 |
| `0x0a` | `recorded_at` | string | required; canonical RFC 3339 UTC with exactly six fractional digits, as spec (c) defines |

A record with `plan_hash` present and one with it legitimately absent
produce distinct, unambiguous canonical bytes: presence is the
structural presence byte, never a sentinel (contract §6.2).

## `plan_hash` presence derivation (contract §2)

The effective plan-bearing state is `recorded_state`, with
`RECONCILING` resolved to the supplied `prior_state`. Where
`recorded_state` is `RECONCILING` and no prior state is available, the
record cannot be encoded and the act does not take effect — fail
closed, per the contract's v0.17 writer obligation.

`plan_hash` is absent exactly when the effective plan-bearing state is
one of the derived no-PlanDoc states — `ROOM_CREATED`, `SCOPED`,
`PLANNING` — and required otherwise. The set is stated with its
derivation (a PlanDoc first exists at T3; a T4 return leaves `PLANNING`
on the absent side; every state from `PLAN_REVIEW` onward is entered
only through T3 or T5) and is re-derived mechanically against the
ratified T1–T22 table by `test/journal-serialization.test.ts`; where a
printed set and the derivation disagree, the derivation governs.

Both positive facts are carried: `recorded_state` always, and
`prior_state` where the recorded state is `RECONCILING` — each
checkable against the lifecycle event named by `lifecycle_event_ref`,
never inferred from a missing field (contract §2). That cross-check is
a 2b verification obligation; this specification fixes the bytes.

## Canonical timestamp and the named 2b obligation

As spec (c), in full: the timestamp must be calendar-valid (the day
exists in that month and year under the Gregorian leap-year rule; a
calendar-impossible timestamp is rejected and has no canonical form),
and the 2b store must reproduce the canonical `recorded_at` form
byte-identically — store the canonical string rather than re-rendering
(ruled 2026-09-01, condition 3).

## Non-retroactivity

Any change to the byte grammar above requires a new spec version with a
new spec identifier; golden vectors bind to the version that generated
them.
